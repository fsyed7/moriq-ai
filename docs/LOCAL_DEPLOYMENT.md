# Windows local deployment

This standalone Compose stack runs the official Open WebUI `v0.11.4` image,
matching the repository's recorded `0.11.4` baseline. It does not build the MORIQ
checkout into the image. MORIQ Brain is installed separately through the native
workspace-model import. The tag is version-pinned, not digest-pinned: record
`docker image inspect ghcr.io/open-webui/open-webui:v0.11.4 --format '{{json .RepoDigests}}'`
after a successful pull. Image/source equivalence and runtime compatibility must
still be checked on the running instance; no automatic version upgrade is used.

See [the actual validation record](LOCAL_DEPLOYMENT_RESULTS.md). Deployment and
Brain activation were blocked, not completed, in the Task 3 execution environment.

## Prerequisites and preflight

Use PowerShell from the repository root. Docker Desktop must be running Linux
containers with a working WSL backend and an accessible engine. Compose 2.24+
supports the optional environment file; validation used Compose 2.31.0.

```powershell
./moriq/local/manage.ps1 Check
docker info
docker system df
Get-PSDrive -PSProvider FileSystem
```

The helper checks CLI/engine access, lists containers/images/volumes, and reports
port 3000 listeners. Check the Windows volume holding Docker's disk image as well
as free space inside Docker. Start refuses less than 10 GiB free on the Windows
system drive as a conservative local policy, not a promised upstream minimum.
More space is needed for local model weights, expanded images and database growth.
Do not retry large downloads on a nearly full disk.

## Existing data and secrets

The external volume is exactly `moriq-webui-data`, mounted at `/app/backend/data`.
The helper creates it only if missing; Compose itself requires it to exist.
It does not delete containers, volumes, images or files. Stop uses `compose stop`.
Start uses `--no-recreate` so it cannot silently replace an existing deployment.

If `moriq-webui` belongs to another Compose project or an earlier `docker run`,
the helper stops with a conflict. Inspect its image, mounts and port binding.
Do not remove or rename it until a migration is explicitly approved. Check for
all other consumers with `docker ps -a --filter volume=moriq-webui-data`.
Never run two Open WebUI instances against the same SQLite database.

For an existing volume, first establish which application version wrote it.
Do not downgrade a database written by a newer release. Back up the entire
volume and the original encryption/session secret to approved storage with
sufficient free space, with the owning application stopped for consistency.
Do not print credentials or upload backups to GitHub.

On a **new** volume, the pinned upstream entrypoint generates a random secret
once at `/app/backend/data/.webui_secret_key`; persistence retains it across
container replacements. No secret is generated by this repository or committed.
On an **existing** instance, preserve its exact original `WEBUI_SECRET_KEY`
(including a key previously stored outside the volume); securely restore it to
the configured key file or provide the original value in the ignored environment
file. Rotating it can invalidate sessions and encrypted data. Do not allow a new
key to be generated against existing encrypted data.

After backup, secret preservation, version and consumer checks, use
`./moriq/local/manage.ps1 Start -ReviewedExistingData` for the first attachment.
The switch records operator review; it is not a backup mechanism or an automatic
migration. An existing container conflict must still be resolved separately.

Optional configuration belongs in `moriq/local/.env`, copied from the adjacent
`.env.example`. It is ignored by Git. Prefer authenticated Admin settings for
provider credentials. Environment defaults do not necessarily override persisted
database settings. Authentication stays enabled. Do not share full `docker inspect`
or expanded `docker compose config` output: it can include secrets; use
`docker compose -f compose.local.yaml config --quiet` for validation.

## Start, stop, restart and verify

```powershell
./moriq/local/manage.ps1 Start
./moriq/local/manage.ps1 Status
./moriq/local/manage.ps1 Stop
./moriq/local/manage.ps1 Restart
docker compose -f compose.local.yaml logs --tail 100 open-webui
```

The helper waits up to 600 seconds for container health, then checks `/ready` and
the root page over HTTP. The health check uses `/ready` so startup and database
readiness matter. First startup may need network access for bundled application
assets/models; inspect logs if it times out. Logs rotate at 10 MB, three files.
The app binds only to **http://127.0.0.1:3000**. Do not change it to `0.0.0.0` or
enable an unauthenticated Docker TCP endpoint to work around engine permissions.

Open the URL and complete the first administrator signup yourself, or sign in to
the existing account. Stop automation at this credential boundary. Do not create
an admin account with generated credentials or reset an existing account. Verify
signup policy and existing accounts before connecting a provider.

The helper deliberately does not apply later environment/image changes to an
existing container. Review and back up first, then separately authorize container
recreation. An HTTP/health success alone does not prove model inference works.

## Model provider and Brain activation

First inspect Admin Panel > Settings > Connections and the available model list
after authorized login. Preserve existing providers, keys, prefixes and defaults.
No connected provider could be established in Task 3: localhost Ollama was also
unreachable. This does not prove there are no persisted remote connections.

Provider options after disk recovery:

| Option | Suitability and remaining checks |
| --- | --- |
| Existing authorized API connection | Small local resource footprint. Requires an existing credential and permission for inference charges/data transfer. Do not create paid accounts or purchase service. |
| Local Ollama, small quantized model | No paid account, but extra disk/RAM required. `qwen3:4b` is a candidate (about 2.5 GB download), not a tested selection. With roughly 7.44 GiB Docker memory, start with one request and a small context; measure actual combined usage before increasing context. GPU/CPU speed, system memory and behavioral quality remain unverified. |

Do not install/download a local model while the disk is full. When Ollama is
available, configure its reachable URL through the Admin UI; Docker Desktop uses
`http://host.docker.internal:11434` for a host provider. Verify reachability from
Open WebUI, not just from the Windows host. Do not expose a provider publicly to
make that connection work. Official references:
[Open WebUI setup](https://docs.openwebui.com/getting-started/quick-start/),
[Qwen3 4B model](https://ollama.com/library/qwen3:4b).

Once a provider responds, obtain the exact connected model ID from Open WebUI,
including any prefix, and generate the import with Python 3.11 or 3.12:

```powershell
$connectedModelId = Read-Host 'Exact connected model ID verified in Open WebUI'
python moriq/brain/build.py --base-model-id $connectedModelId --output moriq/local/artifacts/moriq-brain-0.1.0.json
```

The builder refuses to overwrite an existing output. Use a new reviewed filename
for a later build. Never substitute a guessed model ID just to create an artifact.

After authorized admin login, use Workspace > Models > Import. If `moriq-ai`
already exists, export a backup first and review attached knowledge/tools/filters.
Import can overwrite it and reset sharing. Follow [MORIQ_BRAIN.md](MORIQ_BRAIN.md)
to confirm the real base model, prompt version, private grants and disabled tools.
Do not change the global default. Verify **MORIQ AI** is selectable and responds
in a new chat, then verify intended user visibility.

Run all 12 cases in [the evaluation matrix](../moriq/brain/evaluation.md), at least
three repetitions each. Save exact prompts, outputs, provider/model/settings,
version, date and human PASS/FAIL criteria in ignored local artifacts. Architectural
reasoning, knowledge reliability and Freshie teaching require actual output review;
unit tests cannot establish them. Retrieval/citation UI and access-control checks
are additional gates. Do not label unavailable cases passed.

## Troubleshooting without data deletion

- **Access denied to `dockerDesktopLinuxEngine`:** this session cannot administer
  Docker. Run the helper in an authorized local user session or provide an execution
  environment with engine access. Do not bypass the restriction using exposed APIs.
- **Unexpected EOF during pull:** inspect `%LOCALAPPDATA%\Docker\log\host` and
  `vm`, disk space, engine state and network/proxy connectivity. Task 3 logs show a
  WSL engine shutdown during the pull. Fix available disk space first through
  approved cleanup or relocation. If the engine remains unhealthy, an operator may
  restart Docker Desktop after checking other workloads. Then retry the pinned
  image pull; retained layers can be reused. No prune, factory reset or disk reset.
- **Container-name or port conflict:** inspect the owner and stop for review.
  Do not kill unrelated processes or remove existing containers.
- **Unhealthy startup:** inspect bounded logs and `docker stats --no-stream`.
  Check disk, startup downloads and `/ready`; do not recreate a database to fix it.
- **No models:** inspect authorized connection settings and provider reachability.
  Brain JSON is a prompt configuration, not model weights or a provider.

[Docker troubleshooting](https://docs.docker.com/desktop/troubleshoot-and-support/troubleshoot/)
distinguishes restarting from destructive cleanup/reset operations.
